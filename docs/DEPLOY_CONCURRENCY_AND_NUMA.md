# Deployment: concurrency and PostgreSQL

This document summarizes how **thread/process counts** relate to **PostgreSQL `max_connections`** and large hosts.

**Ini sections:** **`[DEFAULT]`** - install identity, PostgreSQL connection, **`total_cores`**. **`[PORTAL]`** - Gunicorn/Django web tuning. **`[PIPELINE]`** - `sync_timedb`, archive/seal, `update_metrics`, and accounting paths. Integration sections **`[RMQ]`**, **`[SYSLOG]`**, **`[CACHE]`**, **`[XALT]`**, **`[OAUTH2]`** hold the integration settings. See **`hpcperfstats.ini.example`** and **`hpcperfstats/cursor-rules/hpcperfstats-ini-format.mdc`**.

## Services and parallelism (compose)

| Service | Role | Parallelism | DB impact |
|---------|------|----------------|-----------|
| **web** | Gunicorn + Django | Workers = **`[PORTAL] gunicorn_workers`** (default **32**, floor 1); a non-empty **`WEB_CONCURRENCY`** env value replaces it (`services-conf/django_startup.sh`) | Each worker may hold a persistent DB connection (`CONN_MAX_AGE`, default **90s** via `conf_parser.get_db_conn_max_age()`) |
| **web** | `api.py` | `ThreadPoolExecutor` size = **`api_small_executor_max_workers`**, or **`parallel_db_prefetch_max`** (default **4**) when the API key is unset | Extra concurrent ORM work per worker |
| **pipeline** | `update_metrics.py` | Titled in-process thread pool size = **`metrics_pool_processes`**; each thread runs one job's metrics through the baked Codon kernels (`/opt/hpcperfstats/codon_metrics`, `Py_MOD_GIL_NOT_USED`, single-threaded kernels, `OMP_NUM_THREADS=1`). The Bokeh detail/plot **prewarm** then runs in forkserver worker processes, **`metrics_prewarm_processes`** (`auto` = one per metrics thread; `0` = in-thread), titled `[worker:prewarm-pool]`, recycled every **`metrics_prewarm_max_tasks_per_child`** tasks (default 100) | One `COPY (FORMAT BINARY)` reader per job chunk during metrics passes, plus **one connection per prewarm worker process** (counted in the slot budget) |
| **pipeline** | `sync_timedb.py` / archive | Ingest pool = **`get_sync_ingest_pool_processes()`**; archive append pool = **`get_sync_archive_pool_processes()`** - concurrent daily-tar append slots track that pool size (one day per slot). Production coordinator is the **in-process job-store queue orchestrator** (`run_sync_timedb_queue_orchestrator`): exclusive `archive_dir` flock, in-process ingest/append/`day_close` jobs, sliding-window thread pools. **Cold-path** seal -> raw removal -> tar-drop runs on **`day_close` threads** (max **`sync_day_close_max_inflight`**) | See **Day close (queue orchestrator)** and **Archive zstd (shared hosts)** below |
| **pipeline** | `listend.py` | **N competing AMQP consume threads** (`listend_amqp_consumer_count`, default **16**, floor **1**, no upper clamp, one pika `BlockingConnection` each) on the original ingest queue; **host-affine archive threads** (**2 x consumer count**, default **32**; not an INI key) for durable `current` append/rotate + originating-connection threadsafe ack (cheap first-line/`$` host+ts peek, per-host timestamp reorder when N>1, raw AMQP bytes, ack before live-DB submit, sticky flock + kept `current` fd). Drop-mode **`listend_amqp_prefetch`** is **per-consumer** `basic_qos` (default **32**; process-wide unacked = **32xN**; pause keeps prefetch **1** per consumer). Client+broker **`frame_max=131072`**. Optional live DB dual-write via host-affine **threads** (`listend_db_ingest_*`, default **off**; **32** threads when enabled, **8 GiB** total queue budget **hard-capped at 8** so INI values above 8 are clipped; budget is parse-debt + held archive fds; **`listend_db_ingest_batch_samples=100`**, **`listend_db_ingest_flush_max_rows=2000`**, **`listend_db_ingest_flush_hold_s=5`**) sharing ordinary `queue.Queue` objects (no `/dev/shm`, no spawn). Flush is bounded by sample count, pending rows, or hold-age so a never-empty queue still writes Timescale. Backpressure when live on: **`listend_db_ingest_backpressure`** default **`drop`** (archive+ack, shed live DB via `queue_drops`) or **`pause`** (high watermark **0.95** / any worker full -> stop consume without archive until resume **0.50**; overflow on broker). | Low archive path (parallelized across hosts); DB slots when live ingest on - size with `sync_ingest_pool_processes` against Postgres `max_connections`. When live on, archive-backed catch-up remains completeness repair for live gaps; archive/delete needs a sync_timedb file-complete mark |
| **db** | PostgreSQL | `max_connections=500`; `max_worker_processes=32`, `max_parallel_workers=24`, `max_parallel_workers_per_gather=4`, `max_parallel_maintenance_workers=2`; `work_mem=8MB`, `maintenance_work_mem=256MB` in `docker-compose.defaults.yaml` | Hard slot ceiling; per-query memory bounded by GUCs |

**Effective cores:** **`effective_cores = min(ini total_cores, os.cpu_count())`** (`os.cpu_count()` floor 1). If **`[DEFAULT] total_cores`** is **missing** in `hpcperfstats.ini`, the code uses **40**. Pool and worker sizes are absolute INI keys and do not scale with it; `sync_timedb` and `update_metrics` log `effective_cores=` at startup next to their pool sizes.

**Ini reference:** optional tuning keys and defaults are documented in **`hpcperfstats.ini.example`** (one comment per key). The canonical list of wired options is **`INI_OPTION_REGISTRY`** in **`hpcperfstats/dbload/lib/conf_parser.py`**; drift tests in **`hpcperfstats/tests/test_hpcperfstats_ini_example.py`** keep the example aligned.

## Archive zstd (shared hosts)

Daily monitor archives are sealed inside the **`pipeline`** container. **`web`**, **`db`**, and **`pipeline`** share the same CPU scheduler and often the same physical disk (`postgres_data` vs `/data/hpcperfstats_data/site_data`).

| `[PIPELINE]` key | Default | Role |
|----------------|---------|------|
| **`archive_zstd_threads`** | **`4`** | Seal/restore/archive decompress: **`4`** -> zstd **`-T4`** (also the `--threads` default of `scripts/seal_open_daily_tars_to_zst.sh` and `scripts/migrate_daily_archive_gz_to_zst.sh`); **`0`** -> **`-T0`** (all logical cores per zstd process). Compression speed scales with the thread count, so pick **`archive_zstd_level`** at this thread count (see the level row) |
| **`ingest_zstd_threads`** | **`4`** | Ingest/populate sealed streams: **`4`** -> **`-T4`**; **`0`** -> **`-T0`** |
| **`archive_seal_parallel_workers`** | **`2`** | Max daily tar seals running at once (process-wide seal slots); a `day_close` with no free slot yields `reason=seal_slot_busy` and its `day_close` slot does other work. On a saturated shared volume set `1`: one at a time frees each tar's space soonest for the same total time; raise only on storage two seals cannot saturate |
| **`archive_zstd_level`** | **`9`** | Compression level. Also the default `--level` of `scripts/seal_open_daily_tars_to_zst.sh` and `scripts/migrate_daily_archive_gz_to_zst.sh`. hpcperfstats01 2026-11-04, 512 MiB of a daily tar at `-T4` (MB/s in, ratio): L3 757 x4.4, L5 414 x4.6, L7 251 x4.9, **L9 257 x9.1**, L11 150 x9.6, L13 41 x9.7, L15 24 x10.1, L17 16 x18.3, L19 10 x19.0; the archive volume was 100% busy at ~105 MB/s read, and one seal there gets ~24-40 MB/s. Level 9 is the knee: same speed as 7 at twice the ratio, and far above the disk; 13 and up are slower than the disk at `-T4`, and 17-19 halve the file size but run 2-4x slower than the disk. A seal runs at the slower of the disk's per-seal read rate and zstd's compression speed at **`-T<archive_zstd_threads>`**, so choose the highest level whose speed at that thread count stays above the read rate one seal gets on the daily archive volume (total read rate divided by **`archive_seal_parallel_workers`**); above that level seals get slower, below it they only cost ratio. Benchmark with `zstd -b3 -e19 -T4 -S` on a sample of a real daily tar |
| **`sync_pipeline_drop_page_cache`** | **`yes`** | Linux-only **`posix_fadvise`** on pipeline file I/O (ingest streaming, archive zstd, tar paths) |

**Tuning:** If seals are too slow and the disk is not saturated, raise **`archive_seal_parallel_workers`**; on a saturated disk more parallel seals only split the bandwidth. If web/API or Postgres latency spikes during seal/zstd, lower **`archive_seal_parallel_workers`** or **`archive_zstd_threads`**. Archive zstd runs at normal CPU and I/O priority (no `nice`/`ionice` wrapper); space only comes back when a seal finishes. Env **`SYNC_ARCHIVE_SEAL_WORKERS`** overrides the per-call seal worker count inside `seal_dirty_daily_archives` (as **`SYNC_ARCHIVE_VALIDATION_WORKERS`** does for validation fanout); the process-wide seal slot cap (`try_claim_seal_slot`) reads only **`archive_seal_parallel_workers`**.

**Page cache:** Large daily archives and parallel ingest raw reads fill the Linux page cache. With **`sync_pipeline_drop_page_cache=yes`** (default), **`zstd_cli.py`** issues **`POSIX_FADV_SEQUENTIAL`** before large scans and **`POSIX_FADV_DONTNEED`** after one-shot paths and streaming read batches (not a substitute for lowering ingest pool width). Hint only (not **`O_DIRECT`**); macOS dev hosts no-op. **192g pipeline cgroup:** at **60%** file-cache admit, effective cap ~ **117965 MiB** - tune via **`sync_cgroup_admit_max_file_cache_cgroup_pct`** only as an admit tripwire. When the file-cache gate is sticky, empty-inflight **alone-progress** still admits one ingest/append job so fill cannot deadlock at `local_inflight=0`.

## Day close (queue orchestrator)

Ingest is always-on under **`run_sync_timedb_queue_orchestrator`**. Cold-path archive work is **job-store `day_close` jobs** drained by a **`ThreadPoolExecutor`** (max **`sync_day_close_max_inflight`**): age gate -> seal -> `DayRawRemovalCoordinator.apply_batch_delete` -> tar-drop when sealed and no closed raw remains.

| `[PIPELINE]` key | Default | Role |
|----------------|---------|------|
| **`sync_day_close_max_inflight`** | **`8`** | Parallel `day_close` worker threads |
| **`sync_day_close_min_age_hours`** | **`32`** | Min hours after calendar day end before `day_close` may complete |
| **`sync_day_close_raw_paths_per_batch`** | **`1000`** | Incremental raw deletes per `day_close` batch |
| **`sync_ingest_hot_days`** | **`3`** (min **1**) | Hot-band calendar-day window for ingest ZSET scoring (`age < N`: today + prior N-1 days when N>=2; today only when N=1) |
| **`archive_keep_uncompressed_tar`** | **`no`** | Drop prior-day `.tar` at seal when raw is gone; global `yes` retains until tar-drop |
| **`archive_today_uncompressed_tar_grace_hours`** | **`24`** | Keep calendar-today `.tar` after local midnight (hours) when global keep is `no` |
| **`sync_archive_pool_processes`** | **`4`** | Sole knob: archive thread pool workers **and** concurrent daily-tar append slots (one day per slot). On backlog sites with many open daily tars, keep **4+**; one calendar day is always single-writer |
| **`sync_timedb_tar_append_batch_size`** | **`256`** | Max raw paths per append batch (one clone-append job per daily tar; smaller batches finish gate/tvf sooner; pair with site ingest pool as needed). On a reflink filesystem the append clones member data (`FICLONERANGE`) and writes only headers, so batch size does not bound append time |

Progress and `day_close` eligibility are driven by the in-process **job store** plus reconstruct from disk/Timescale (checkpoint `.sync_timedb_state.json` is **not** reconstruct source of truth). `day_close` jobs refill continuously up to **`sync_day_close_max_inflight`**. Append slots (**`sync_archive_pool_processes`**) and `day_close` slots are fixed caps, one calendar day / daily tar per slot; overflow days drain when a slot finalizes.

**Multi-week backlog / disk pressure:** raise **`sync_day_close_max_inflight`** and keep **`sync_day_close_raw_paths_per_batch`** high enough for your daily file count (e.g. 15k/day may need several internal batches within one `day_close` worker pass). Default **`archive_keep_uncompressed_tar=no`** drops prior-day `.tar` at seal once raw is gone; calendar-today keeps `.tar` for **`archive_today_uncompressed_tar_grace_hours`** (default 24h after local midnight). Set global **`archive_keep_uncompressed_tar=yes`** during heavy same-day append if you need the uncompressed `.tar` for late raw appends.

## OOM and `sync_timedb` process tree

Ingest workers are threads inside the `sync_timedb.py` process (`SyncTimedbThreadPool`, role `ingest-pool`), so a multi-GiB anon spike while parsing a giant raw segment counts against that process. File parses on the free-threaded image run in Codon worker processes (`python -m hpcperfstats.dbload.lib.codon_process_worker`, one per concurrent file, at most `MAX_CODON_SLOTS` = 128). A kernel or cgroup OOM kill of one fails that file's parse with `codon worker EOF rc=-9`, and the slot starts a fresh worker on its next checkout.

| Mitigation | Role |
|------------|------|
| **`PR_SET_PDEATHSIG` (SIGKILL)** on `update_metrics` prewarm worker processes (`apply_pool_worker_process_title`) | Prewarm workers exit when `update_metrics.py` dies so **supervisord** can restart a clean tree. Codon parse workers do not set it |
| **`pipeline` `mem_limit` / `memswap_limit`** (Compose) | Cgroup cap before host global OOM on swapless hosts; **128 GiB** fits a **192 GiB** RAM host; set it per site in `docker-compose.yaml` (commented `mem_limit: 128g` / `memswap_limit: 128g` in `docker-compose.yaml.example`). Without it `memory.max` is `max` and ingest has no memory budget |
| **`rabbitmq` `mem_limit` / `memswap_limit` 96g** plus **`vm_memory_high_watermark.absolute = 64GiB`** | Cgroup hard wall at 96 GiB; publishers block at 64 GiB (~32 GiB headroom) (`services-conf/rabbitmq_vm_memory.conf`) before Erlang `binary_alloc`. **`ERL_FLAGS=+MBas aobf +MBlmbcs 512 +MHlmbcs 512`** reduces allocator fragmentation. Console **`warning`** (not **`info`**); **`ERL_CRASH_DUMP_SECONDS=0`**. Recreate `rabbitmq` after changing limits, watermark, logging, crash-dump knobs, or **`ERL_FLAGS`**. Lower both mem limits and watermark together on hosts with less than 96 GiB RAM. Recovery: **`docs/OPERATOR_RABBITMQ_RECOVERY.md`**. |
| **`sync_ingest_max_file_read_bytes`** (default **512 MiB**) | Stream-parse larger segments instead of **`readlines()`** |
| **`sync_ingest_parse_flush_max_mib`** (default **512**) | Soft max MiB per streaming parse->write flush chunk (sample-boundary overage OK). Sole operator batch-size knob for sync_timedb flush sizing. Default write path is COPY->staging->`ON CONFLICT` (see `sync_timedb_host_data_insert` / `sync_timedb_proc_data_insert`); opt out with `HPCPERFSTATS_SYNC_HOST_DATA_COPY=0` / `HPCPERFSTATS_SYNC_PROC_DATA_COPY=0` |
| **`sync_ingest_pool_processes`** (default **64**) | **Parse** pool width (threads on 3.14t) and archive metadata discovery threads; **in-flight ingest leases equal parse pool size**. **Do not raise above 64 (toward 96/128)** without watching census `job_store_wait_s` / `job_store_hold_s` and confirming `[thread:job-store-persist]` owns sidecar I/O - parse=128 on a deep ZSET can futex-stall claim/ACK when wait tokens dominate (see `OPERATOR_SYNC_TIMEDB_STALL_VERIFY.md`). Also the Codon file-parse **worker process** count: one worker per ingest thread (capped at `MAX_CODON_SLOTS` = 128), each with its own Codon runtime + Boehm GC (threads sharing one runtime serialize on Boehm's allocation lock). There is no separate worker-count knob. Dev host (w64, 100g cgroup, 1 MiB windows): **32 workers** peak 29.0 GiB combined worker RSS / 56.9 GiB cgroup, **64 workers** 35.5 GiB / 64.7 GiB, no OOM; both DB-bound at ~155-160k `tup_inserted`/s. Worker RSS counts toward the tree RSS roof (`sync_process_tree_rss_limit_cgroup_pct`): on Horizon (51.2 GiB roof) lower this key to 32 if ingest admit defers |
| **`sync_codon_parse_flush_max_mib`** (default **1**) | Codon parse window (MiB of input). Worker heap follows **output rows**, not input bytes: densest corpus files peaked at 5.7-7.7 GiB/worker with 16 MiB windows, 0.9-1.1 GiB with 1 MiB. Host COPY rows are re-merged to `_ingest_write_frame_slice_rows()` (10k) per write so small windows do not create tiny transactions (`LWLock/LockManager` stalls); proc rows are never merged (`ON CONFLICT DO UPDATE`). |
| **`sync_codon_worker_recycle_rss_mib`** (default **1536**) | A Codon worker whose RSS exceeds this is replaced **between** files (the Boehm heap never shrinks after a dense file). A hard heap cap (`GC_MAXIMUM_HEAP_SIZE`) aborted workers mid-file and is not used. |
| **`sync_ingest_write_pool_processes`** (default **0** -> **1/2 parse**) | Max concurrent ingest DB sessions / write threads. Connection budget uses **this** width, not parse width. Default **32** when parse=64 (**64** when parse=128). |
| **`sync_ingest_parse_queue_max`** (default **0** = 2x `sync_ingest_pool_processes`) | Bounded parse->write queue slots (payload count). Fill refuses new parse when full; in-flight parse **blocks on `put`**. Census: `parse_put_block_s` / `_max_s` / `_n`. |
| **`sync_ingest_malloc_trim_after_file`** (default **no**; set **`yes`** on Horizon / hpcperfstats04) | Linux **`gc.collect()`** + **`malloc_trim(0)`** after each ingest pool task; full release also clears daily archive member L1. **Why default `no` (dev soak, Codon on, width 64):** the per-file `gc.collect()` is stop-the-world on free-threaded 3.14t and held ~80% of wall time (178 collections, 852 s of 1066 s). `no` measured **225-255 MiB/min vs 84-101** (n=3 vs n=5) at width 64 and **127-175** at width 32 (n=3), with RSS max **24 GB -> 51-64 GB** (w64) / **32 GB** (w32). `malloc_trim` is a no-op under the image's `LD_PRELOAD` jemalloc (probe: RSS unchanged after free, `gc.collect()`, `malloc_trim`, and a 25 s jemalloc decay window), so `no` loses only the `gc.collect()`. Set `yes` where the tree RSS roof is too small (Horizon: 128 GiB cgroup, 40% roof = 51.2 GiB; Stampede3: 256 GiB cgroup, roof 102 GiB, fits `no` at width 64). The default `no` assumes a roof (`sync_process_tree_rss_limit_cgroup_pct` x `memory.max`, 52428 MiB on a 128 GiB cgroup) is above the observed peak; above the roof ingest admit defers. Rate check needs no telemetry: `scripts/measure_pipeline_ingest_rate.py` (`sync_full_ingest_mib_per_min`) |
| **`sync_process_tree_rss_limit_cgroup_pct`** / **`sync_process_tree_rss_exit_cgroup_pct`** (default defer **40** on **128 GiB** cgroup -> effective roof **52428** MiB) | Tree roof scales with runtime **`memory.max`**: effective MiB = ``(max x pct // 100) // (1024x1024)``; in-flight raw admit budget = ``effective_roof_bytes / PEAK_CGROUP_PER_RAW_FILE_BYTE`` (**1.0** -> budget ~ roof ~ **52428** MiB raw at default on **128g**; no separate budget INI). **40%** leaves ~**76 GiB** of the **128g** pipeline cgroup outside the sync soft roof for **listend** / **update_metrics**. **`limit_cgroup_pct=0`** disables defer and the byte budget (fail open when ``memory.max`` unknown). Exit pct optional hard exit (**0** = off). Fair-share cooperative recycle remains post-task only. **RSS-pressure admission gate (no separate INI key):** the same roof also gates *new* ingest admission on measured sync tree RSS - at or above the roof `_fill_ingest_band` is skipped (`fill_block=skip_rss_pressure`, log `queue_orchestrator rss_hold rss_mib=... limit_mib=... inflight=...`, 30 s rate limit, `suppressed_n=`) while completions keep draining; with nothing in flight and RSS still over the roof one `gc.collect()` + `malloc_trim` runs (`rss_release rss_mib_before=... rss_mib_after=...`) and admission resumes. This is the release-off memory control (the raw-byte budget does not track release-off RSS: measured RSS / in-flight raw ranged 5-57x). Dev soaks (128 GiB cgroup, width 64, release off): roof 30% = 39321 MiB -> 286 MiB/min, gate held once; roof 15% = 19660 MiB -> 184 MiB/min, RSS 11-30 GiB, gate held for minutes; uncapped 275 MiB/min peaking at 42.8 GiB. `rss_release` has not fired in any soak (RSS fell under the roof when the first file cohort completed); it is covered by unit tests only. Verify on a site: full pipeline log filtered for `rss_hold\|rss_release` (`docs/OPERATOR_SYNC_TIMEDB_STALL_VERIFY.md`) |

**In-flight raw-byte admit:** ingest threads share one heap, so slot count alone can put many multi-GiB files in memory at once. **`_fill_ingest_band`** admits a file only when ``sum(inflight st_size) + candidate`` fits the in-flight raw budget (effective tree roof / `PEAK_CGROUP_PER_RAW_FILE_BYTE`, which is **1.0**, so the budget equals the roof); otherwise it requeues the job (`skip_budget_bytes`). A file larger than the budget is admitted alone when nothing is in flight. While blocked, the census line appends ``ingest_mem_blocked=yes inflight_raw_mib=... budget_mib=...``. Pool width is not concurrent raw volume. Two cgroup gates also apply to multi-file ingest admit and to append fill: **`sync_cgroup_admit_headroom_mib`** (default **4096**; ``0``=off) requires ``memory.max - (memory.current - inactive_file)`` MiB free (`skip_cgroup_headroom`), and **`sync_cgroup_admit_max_file_cache_cgroup_pct`** (default **60**; ``0``=off) blocks while cgroup ``memory.stat`` ``file - inactive_file`` exceeds ``memory.max x pct`` (`skip_file_cache_pressure`). An oversized file admitted alone passes the headroom gate, and the file-cache gate still admits a file while at most one other is in flight. `skip_budget_bytes`, `skip_cgroup_headroom` and `skip_file_cache_pressure` requeue **without an attempt bump**, so they never dead-letter. **`sync_ingest_stuck_inflight_recycle_s`** (default **3600**; ``0``=off) requests an ingest pool recycle through the MainThread pause protocol when the oldest in-flight submit is older than the threshold (mem-telemetry event `stuck_cohort_recycle`); collateral jobs requeue without an attempt bump. Post-ingest raw **`POSIX_FADV_DONTNEED`** follows **`sync_pipeline_drop_page_cache`** (default yes). Every gated line: **`sync_timedb_mem_telemetry=yes`**. On **8-16 GiB** dev compose set **`sync_cgroup_admit_max_file_cache_cgroup_pct=0`** with **`sync_process_tree_rss_limit_cgroup_pct=0`**.

**Catch-up INI starting points** (until a backlog of multi-GiB segments clears): the defaults in **`hpcperfstats.ini.example`** are **`sync_ingest_pool_processes=64`**, **`sync_ingest_malloc_trim_after_file=no`** (set `yes` where the tree RSS roof is small, see the table above), **`sync_process_tree_rss_limit_cgroup_pct=40`**. On **small dev compose** hosts (e.g. 8-16 GiB pipeline cgroup), set **`sync_process_tree_rss_limit_cgroup_pct=0`** to disable tree defer **and** the file-size admit gate (slot-only) and optionally lower **`sync_ingest_pool_processes`** if RAM-bound. Discover admits up to **`sync_ingest_queue_max_size`** catchup files (default **50000**); files skipped past it are found again by the next whole-archive walk (**`sync_ingest_full_rescan_interval_hours`**, default **6**, or sooner once the queue drains to half the cap). On very large trees (~100k+ closed paths), tune **`sync_day_close_max_inflight`** (default **8**, pipeline occupancy and parallel workers). Ingest never waits for `day_close`.

**`day_close` progress grep:** `queue_orchestrator day_close claim`, `queue_orchestrator day_close stage_enter`, `queue_orchestrator day_close stage_exit`, `queue_orchestrator day_close vacate` (`outcome=`).

**Discovery:** the orchestrator streams `fdfind`/`fd -X` GNU `stat --printf` records (`sync_timedb_stats_find`: path/mtime/size/inode; there is no GNU `find` fallback) into the ingest queue, so discovery does **not** re-`os.stat` fields stat already emitted. The idle pass walks files changed within **`sync_ingest_rescan_mtime_days`** (default **1**); whole-archive walks run at boot and every **`sync_ingest_full_rescan_interval_hours`**.

**Forensics checklist:** inside the pipeline container read `memory.max`, `memory.current`, `memory.peak`, `memory.events` (`oom_kill`); `ps -eo pid,rss:10,cmd` for the `codon_process_worker` processes vs the `sync_timedb.py` main process; `find` largest raw stats paths. Log a short packet under **`test_runs/`** when investigating.

**Docker/cgroup OOM vs kernel OOM:** cgroup kills often leave **host `dmesg` empty**. Inside the pipeline container:

```bash
docker compose exec pipeline sh -c '
  cd /sys/fs/cgroup || exit 1
  echo "=== memory.events ==="
  cat memory.events
  echo "=== memory.current / max / peak ==="
  for f in memory.current memory.max memory.peak; do
    printf "%s: " "$f"; cat "$f" 2>/dev/null || echo n/a
  done
'
```

| `memory.events` field | Meaning |
|-----------------------|---------|
| `oom_kill` | Processes SIGKILL'd by the **container memory cgroup** (non-zero => Docker/cgroup OOM in this container lifetime) |
| `oom` / `oom_group_kill` | Related cgroup OOM counters |

Also: `docker inspect <pipeline_container> --format '{{.State.OOMKilled}}'` (main PID only). **`memory.events` counters reset** when the container is recreated - compare `StartedAt` and historical `docker events` if investigating a past incident.

Size the tree RSS roof together with `metrics_memory_budget_pct` (see **Shared limit** under **update_metrics memory admission**); grep kernel logs for `oom-kill` + `sync_timedb.py` and correlate with the `queue_orchestrator` lines in application logs.

## update_metrics memory admission

`update_metrics` runs up to `metrics_pool_processes` jobs at once and admits them by estimated memory as well as by count (`docs/UPDATE_METRICS_STATE_MACHINE.md`, sliding session admission). Count alone would let a burst of large backfill jobs (each holding its fetch peak, a parked `HANDOFF` frame, a copy shipped to its prewarm worker and the plot objects) drive the process past host memory. Memory admission keys:

| Key (`[PIPELINE]`) | Default | Effect |
|---|---|---|
| `metrics_memory_budget_pct` | 40 | Estimated memory of all in-flight jobs (`estimated_sample_count` x learned rows per host-minute, floored at `METRICS_ROWS_PER_HOST_MINUTE`, x `METRICS_PEAK_BYTES_PER_ROW`, plus the metrics pivot grids, linear in host-minutes; measured frame rows once a job's metrics finish) stays under this percent of the pipeline cgroup `memory.max`, or of host `MemTotal` when the cgroup is unlimited. One job always runs alone. `0` = count cap only. |
| `metrics_memory_budget_head_wait_s` | 600 | A job too large for the free budget may be passed by smaller jobs for this long; then its lane (both lanes for a fresh job) waits for it. |
| `metrics_admit_headroom_mib` | 16384 | No new job starts while another runs when headroom is below this: cgroup `memory.max - (current - inactive_file)`, or host `MemAvailable` when unlimited. `0` = off. |

Budget derivation: production jobs on hpcperfstats04 carry 238-335 frame rows per host-minute (the single-host golden corpus ran about 200), and the float64 fetch plus compute peak is 122-144 bytes per row on frames above a few thousand rows. The cost model therefore floors rows per host-minute at the production p90 (`METRICS_ROWS_PER_HOST_MINUTE`), learns a higher value from finished jobs, and switches a job to its measured frame size once its metrics finish. Large multi-host jobs peak far above that per-row figure while metrics run, almost all of it metrics pivot grids. The pivot cache is bounded by `PIVOT_CACHE_MAX_BYTES` (least recently used evicted, an evicted type pivots again with the same values), `get_type` returns read-only views, pivots hold one row per (host, sample time) pair of a type (value and arc), so a grid is linear in host-minutes, and the cost adds the largest grid plus the cache, floored at `METRICS_GRID_BYTES_PER_HOST_MINUTE` per host-minute (the widest type's events x 16 bytes x pairs per host-minute, measured on a 162-host x 551-minute unaligned synthetic tiled from a single-host golden job whose widest type has 38 events) and learned from finished jobs as grid bytes per host-minute (`grid_b_hmin:` in the census `admit=` group). The headroom gate stays the measured backstop: it only stops new jobs, so jobs already in flight can still grow. With work in flight the once-a-minute `metrics census` line carries `mem_gib=handoff:,rss:,est:,meas:,budget:` and `admit=inflight:,rows_hmin:,grid_b_hmin:`; `rss` well above `est + meas` means memory no in-flight job accounts for (allocator retention or a leak).

**Shared limit:** update_metrics, `sync_timedb` (its tree RSS roof `sync_process_tree_rss_limit_cgroup_pct`, its ingest pool and any `sync_ingest_*` workers), `listend` and the prewarm worker processes all draw on the same pipeline cgroup `memory.max`, and neither budget counts the others. Keep `metrics_memory_budget_pct` plus the `sync_timedb` roof percent well under 100 (at the defaults they total 80) so listend and the prewarm children fit beside them; on a host where ingest runs near its roof, lower `metrics_memory_budget_pct` rather than relying on the headroom gate.

## Archive recovery (operators)

Raw stats on disk remain the **source of truth** until validated archive membership, DB ingest gate (when enabled; **`sync_archive_require_db_ingest=yes`** requires first **and** last digit-leading timestamp seconds in `host_data`, via streaming head + EOF-backward tail reads), and `day_close` raw removal all succeed.

| Symptom | Safe recovery |
|---------|----------------|
| **Bad `.tar.zst`, good legacy `.tar.gz`** | Remove or rename the corrupt `.tar.zst`; restore sibling `.tar` from gzip (`decompress_compressed_to_tar` / `zstd -d --format=gzip`). Raw stats stay until validation passes. |
| **Sealed `.tar.zst` unreadable for ingest lookup** | Check `zstd -t /path/YYYY-MM-DD.tar.zst`. If **passes** but tar stream fails (`unexpected end of data`), the tar **payload** is truncated - prefer sibling **mutable `.tar`** when `tar tf` passes (populate auto-fallback; clears stale `archive_day_ingest_skip` when sealed is gone). **`sync_timedb`** and operator scripts may **repair truncated `.tar` in place** (`repair_truncated_daily_tar_in_place`) when members remain extractable; otherwise restore/re-seal from legacy `.tar.gz`. Validate pairs with **`scripts/verify_open_tar_matches_zst.py`**. If **`zstd -t` fails**, the zstd frame is corrupt. When both sealed stream and tar scan fail, ingest logs **`ERROR: daily sealed archive unusable for ingest lookup`** once per day (`reason=zst_frame_invalid` or `tar_truncated_or_unreadable`), sets store **`archive_day_ingest_skip`**, and skips tar-append duplicate-check until repair. **`atomic_seal_tar_to_zst`** refuses seal when tar fails **`verify_tar_archive_readable`**. Active-ingest decompress for append keeps sealed sibling (`remove_compressed=False`). DB-complete ingest continues (`need_archival=False` for skipped days). |
| **Missing `.tar` after mistaken drop** | Decompress sealed `.tar.zst` (or legacy `.tar.gz`) to sibling `.tar` before append; never delete raw while tar/zst validation fails closed. |
| **Persistence contract version mismatch** | On startup, **`ensure_persistence_contract`** compares **`{archive_data_dir}/.sync_timedb_persistence.json`** to the built-in version. Mismatch logs **`persistence reset old=... new=...`** and deletes all registered **`.sync_*`** sidecars (checkpoint, hints, manifests) so ingest/archive reprocesses from scratch - no manual sidecar delete is needed. |
| **Corrupt daily `.tar` before append** | `replace_corrupt_tar_from_compressed_backup` tries zst then gz; append stays fail-closed (`False`) if restore fails - raw files remain. |
| **Head+tail ingested, gaps in the middle** | Gate checks first and last digit-leading timestamp seconds only (no full-file scan); missing middle segments may still pass - head-only or tail-only partial ingest fails. Treat unexpected raw deletion as incident-driven review, not routine ops. |
| **Unparsable closed raw blocking a day** | Inspect **`{archive_data_dir}/.sync_timedb_unparsable_raw.json`** and **`{archive_data_dir}/.sync_timedb_unparsable_raw/`**; ingest moves permanently unparseable closed raw off the hot tree when parse fails (quarantine reason `ingest_parse_failed`). Restore only after fixing content or deliberate operator review - do not delete manifest entries casually. Parsable-but-unmapped raw still blocks until ingest/archive catches up. |
| **`day_close` seal/delete/tar-drop on `day_close` threads** | Queue orchestrator **`_run_day_close_job`**: age gate -> **`seal_dirty_daily_archives`** -> **`DayRawRemovalCoordinator.apply_batch_delete`** -> drop uncompressed `.tar` when `.tar.zst` exists and no closed raw remains. Grep: **`queue_orchestrator day_close`**. |

## PostgreSQL connection budget (operator)

Rough peak connections (code: ``estimate_django_pg_slot_peak()``):

`gunicorn_workers x max(api_small_executor_max_workers, parallel_db_prefetch_max) + listend_db_ingest_pool_processes + metrics_pool_processes + metrics_prewarm_processes + public_ef_pool(4) + sync_ingest_pool_processes + sync_day_close_max_inflight + sync_archive_pool_processes + reserve(32)`

Example (INI defaults): `32 x 4 + 32 + 32 + 32 + 4 + 64 + 8 + 4 + 32 = 336` - under **`max_connections=500`** and the **400** WARN threshold. The estimate counts ingest at parse width (`sync_ingest_pool_processes`); concurrent ingest DB sessions are bounded by **`sync_ingest_write_pool_processes`** (default **1/2** of parse **64** -> **32**), so the ingest term is an upper bound. A census of hundreds of **idle** backends from `pipeline` is a **leak** (detached `update_metrics` threads after `reset_pool_hard` whose Django sockets were not `connections.close_all()`'d). **Do not raise the GUC** to paper over that; worker `finally` must close thread-local backends because `CONN_MAX_AGE` never fires on abandoned threads.

Compose sets **`max_connections=500`** with **reduced `work_mem` / parallel gather / maintenance buffers** to limit RAM spikes while keeping slot headroom. The stack does **not** use an external pooler (no PgBouncer): sizing is direct Django -> Postgres. Still use **`WEB_CONCURRENCY`**, **`metrics_pool_processes`**, **`sync_ingest_pool_processes`**, and **`parallel_db_prefetch_max`** so concurrent heavy queries stay bounded. Startup logs a **WARN** at **80%** of 500 (`log_pg_slot_budget_if_needed`); that check is log-only.

## Connection lifetime, query timeouts, and staggered pipeline

- **`CONN_MAX_AGE`:** Default **90** seconds (`[PORTAL] db_conn_max_age` or **`DJANGO_CONN_MAX_AGE`**). Lowers how long idle Gunicorn workers hold a backend. Does not cap peak concurrency under full load; pairs with the caps above.
- **`statement_timeout` / `idle_in_transaction_session_timeout`:** Defaults **120000 ms** and **300000 ms** for PostgreSQL sessions via Django **`OPTIONS`** (`conf_parser.build_postgres_connection_options()`). The **`db`** service in **`docker-compose.defaults.yaml`** sets the same server parameters so non-Django clients inherit them. Disable per-session timeouts by setting **`DJANGO_DB_STATEMENT_TIMEOUT_MS=0`** and **`DJANGO_DB_IDLE_IN_TRANSACTION_TIMEOUT_MS=0`** (and adjust compose if you remove server defaults). Tune upward only if legitimate bulk jobs hit the limit.
- **`update_metrics` thread workers:** do **not** raise global `db_statement_timeout_ms` for long `host_data` compute. Use **`[PIPELINE] metrics_worker_statement_timeout_ms`** (default **120000**; env **`HPCPERFSTATS_METRICS_WORKER_STATEMENT_TIMEOUT_MS`**; **`0`** disables session timeout during `compute_metrics`). Non-zero values arm metric-row `host__in` chunk-on-timeout splitting; parent no-progress detection remains `metrics_run_stall_timeout_s`. Parent persist uses **`metrics_persist_statement_timeout_ms`**. Each columnar `host_data` COPY (8 hosts x <=15 min) runs in its own transaction with **`[PIPELINE] metrics_copy_statement_timeout_ms`** (default **600000**, below the 900 s stall clock; **`0`** disables; not applied under gunicorn): the read is a bounded index scan whose cost is the rows it reads, so on slow storage (hs04 2026-11-02, ~10 ms reads during a 50 T `fstrim`) a 120 s cancel only made the host bisect re-read the same rows. Simple-metric ORM probes also skip types/events absent from `jid_table.schema` (same idea as SummaryPlot).
- **Staggered supervisord jobs:** [`services-conf/supervisord.conf`](../services-conf/supervisord.conf) starts **`listend`** first (higher priority), then **`sync_timedb`** after **20s**, then **`update_metrics`** after **90s**, then **`ingest_coverage_sweeper`** after **120s**, so restarts do not open every DB pool at the same instant. Drain programs (**`hpcperfstats-rabbitmq-listener`**, **`sync_timedb`**, **`update_metrics`**) set **`stopsignal=TERM`**, **`stopasgroup=true`**, and **`killasgroup=true`**. **`rabbitmq-watcher`** and **`rsync_data`** set **`stopsignal=KILL`**, **`stopasgroup=true`**, **`killasgroup=true`**, and **`stopwaitsecs=1`**. The start **`sleep`** lines are boot stagger only; on stop, supervisord signals programs without those sleeps. **`rsync_data`** runs via **`rsync_data_wrapper.sh`** (prefers `rsync_data.sh`, else `rsync_data.sh.example`); both payloads idle behind a 12h sleep/exit guard until operators enable them.
- **Graceful stop / `stopwaitsecs`:** `sync_timedb` cooperative drain is capped by **`SHUTDOWN_DRAIN_TIMEOUT_S` (120s)**. The tracked config sets **`stopwaitsecs=130`** on the three drain programs; **`ingest_coverage_sweeper`** also stops on **`TERM`** as a group with **`stopwaitsecs=70`**. Compose **`stop_grace_period`** defaults to **30s** for **`web`** (`HPCPERFSTATS_WEB_STOP_GRACE`) and **480s** for **`pipeline`** (`HPCPERFSTATS_PIPELINE_STOP_GRACE`); **`db`** (and dual-run **`db_pg18`**) and **`rabbitmq`** get **30m** so Postgres (SIGINT fast shutdown, checkpoint) and the broker (quorum/mnesia) finish before SIGKILL. **`scripts/rebuild_pipeline.sh`** **`HPCPERFSTATS_PIPELINE_STOP_TIMEOUT`** defaults to **480** and **`HPCPERFSTATS_WEB_STOP_TIMEOUT`** stays **30**. A shorter pipeline override SIGKILLs mid-drain. SIGTERM-driven exit **143** is the T0 expectation in [`OPERATOR_SYNC_TIMEDB_STALL_VERIFY.md`](OPERATOR_SYNC_TIMEDB_STALL_VERIFY.md) when wall clock covers drain.

## Absolute pipeline / portal pool sizes

Pool sizes are absolute INI keys: `sync_ingest_pool_processes` (default **64**), `metrics_pool_processes` (default **32**; in-process metrics threads), `metrics_prewarm_processes` (default **`auto`** = one prewarm worker process per metrics thread), `gunicorn_workers` (default **32**), `listend_db_ingest_pool_processes` (default **32**).

**Backfill lane slot share:** behind the fresh 7-day window `update_metrics` recomputes every older job whose `job_data.metrics_version` is NULL or older than `METRICS_CONTRACT_VERSION` (`lib/metrics.py`), newest first, plus old jobs that ingest stamped dirty. The lane's slot cap is **work-conserving**: `max(metrics_backfill_min_slots, metrics_pool_processes - metrics_backfill_fresh_reserve_slots - fresh jobs active)`. With the fresh window idle (the common case) the sweep runs on every thread but the reserve (32 threads, reserve **2** -> 30 slots); as fresh jobs are queued the cap shrinks one-for-one down to the floor **`metrics_backfill_min_slots`** (default **0** = `metrics_pool_processes // 5`, at least 1; 32 -> 6). The consumer always pops fresh-window jobs before backfill jobs and **`metrics_backfill_fresh_reserve_slots`** (default **2**) threads are never given to the lane, so a fresh job arriving mid-sweep starts immediately instead of waiting for a backfill job to finish. Each backfill job is one `COPY (FORMAT BINARY)` reader plus the prewarm, like a fresh job; on sites where the extra `host_data` reads must stay below a ceiling set **`metrics_backfill_max_jobs_per_hour`** (default **0** = unlimited). The lane keeps a scheduler pass open while old jobs remain and relists the fresh days in place every `metrics_scheduler_pass_interval_s`, so the sweep runs continuously at the slot share; **`metrics_backfill_enabled = no`** turns it off (dirty catch-up of processed jobs stays). A bump of `METRICS_CONTRACT_VERSION` makes every job stale, so the whole database is swept again (newest first). `update_metrics.py --backfill-status` prints the remaining counts; the once-a-minute `metrics census` line carries `backfill=slots:k/n,...` and the hourly-refreshed `backfill_db(hourly)=stale:,...`. Details: `docs/UPDATE_METRICS_STATE_MACHINE.md` section 4.5.

**Metrics thread reset:** `update_metrics` stall recovery detaches the current executor, cancels Futures that have not started, and creates a fresh titled pool lazily. Python cannot kill a running thread; database statement/lock timeouts must bound ORM work, while `metrics_run_stall_timeout_s` lets the scheduler soft-fail pending JIDs and continue. Operators should see `[thread:metrics-pool]` and `[thread:public-ef-pool]` threads under one `update_metrics.py [main]` process, plus the forkserver Bokeh prewarm worker processes (`prewarm-pool`, see **`metrics_prewarm_processes`**).

**Free-threaded pool scaling:** on the 3.14t pipeline interpreter `update_metrics.py` imports `hpcperfstats/analysis/metrics/lib/plot/bokeh_validation_patch.py` before any `bokeh.models` import; the shim hoists the per-call imports of Bokeh's `PropertyDescriptor.is_unstable` (Bokeh is pinned at 3.10.2 in `pyproject.toml`). Prewarm time is ~94% Bokeh, mostly job *detail* artifacts and `json_item`. Bokeh model construction in threads serialises on the `sys.modules` dict and `_abc` cache set locks (measured on hpcperfstats-dev, 28 cores, 108 cloned jobs: threads peak at 16 with 7.3 jobs/min; 28 threads 6.6), so the prewarm runs in worker processes: 8 / 16 / 28 processes give 13.4 / 25.8 / 40.4 jobs/min (near-linear), and the parent carries no Bokeh garbage. The remaining parent cost at width is the **stop-the-world cyclic GC** (whole-heap scan per collection; ~8% of wall at 8 threads): **`[PIPELINE] metrics_gc_threshold`** (default **0** = interpreter default) is passed to `gc.set_threshold` at scheduler start, and the `metrics census` line reports collections as **`gc=n:,pause_s:`** so the trade (fewer pauses vs more uncollected Bokeh cycles between them) can be read off production logs before raising it. `gc.freeze()` does not shorten FT collections (measured) and is not used.

**MKL / OpenMP:** `update_metrics` calls `configure_blas_thread_env()` before numpy so inner BLAS/VML threads default to **1**. Outer parallelism is **`metrics_pool_processes`**. Operator env (`MKL_NUM_THREADS`, `OMP_NUM_THREADS`, `NUMEXPR_NUM_THREADS`, and the other `setdefault` keys) still wins. Do not raise inner BLAS threads to match core count while the metrics pool is large - that oversubscribes.

### Metrics window-coverage readiness (summary plots)

By default **`update_metrics`** defers each job until in-window `host_data` samples exist within configurable margins of Slurm **`start_time`** and **`end_time`** (job aggregate: any accounting host may satisfy each edge). Defaults: **`metrics_readiness_require_window_coverage = yes`**, **`metrics_readiness_start_margin_seconds = 600`**, **`metrics_readiness_end_margin_seconds = 600`**.

Jobs with long monitor prolog gaps (telemetry begins hours after Slurm start) stay deferred until early-window data exists or an operator disables the gate. Set **`metrics_readiness_require_window_coverage = no`** in **`[PIPELINE]`** only for recovery/backfill emergencies. When metrics run, **`telemetry_first_time`** / **`telemetry_last_time`** on **`job_data`** and plot artifact fingerprints incorporate those bounds so backfill invalidates stale summary plots.

**Scoping:** strict readiness and the coverage proxy both use **`job_data.host_list`** hostnames (FQDN) and the Slurm window - not **`host_data.jid`**. Any in-window sample on an accounting host may satisfy a margin (including samples from other jobs on shared nodes during overlapping wall-clock windows). That trade-off fixes tail-only false-ready bugs but is weaker than per-jid isolation.

**Permanent defer / stall watchdog:** jobs whose telemetry never reaches both margins (for example multi-hour prolog gaps with default 600s margins) remain in the deferred-not-ready map with **`metrics_deferred_not_ready_retry_s`** (default **10**) retries, then **`metrics_deferred_not_ready_quarantine_s`** (default **300**) intervals - they are not dropped from candidacy while still in range. Large historical backfills of such jobs increase readiness-thread DB load and can keep compute workers idle; disable the gate or reduce margins for emergency backfill, and watch scheduler stall metrics.

**Gate failure stamp:** when the coverage gate fails (`start_ok=False` or `end_ok=False`), **`update_metrics`** removes persisted metrics rows and plot/detail artifacts for that job, writes the full metrics catalog with **`no_data_reason = "Insufficient Data For Metrics Processing"`**, and keeps the job in the daily candidate list (via **`gate_failure_recheck`** in **`_jobs_queryset`**) on every scheduler run until margins pass and **`Metrics.run`** succeeds. Jobs that ingest stamps **`metrics_dirty_at`** (late `host_data`) are listed again as well. 

**Performance:** readiness batches dedupe host aggregates across jobs sharing the same window; precomputed bounds are passed into **`Metrics.run`** to avoid a second in-window aggregate during persist.

## Day close and seal/append lock contention

`day_close` sizing is in **Day close (queue orchestrator)** above.

**Seal vs append:** `atomic_seal_tar_to_zst` holds an exclusive **`file_write_lock`** on the daily `.tar` for the full compress/replace window. Hot-path append uses the same lock (default **60s** timeout). Large-day seals during ingest can surface append **`TimeoutError`** (fail-closed). Mitigations: use **`archive_keep_uncompressed_tar=yes`** (or rely on today's grace window) during heavy same-day append, isolate **`pipeline`** CPU budget from **`web`**/**`db`** when possible, and rely on `day_close` yielding to the hot path when ingest or populate needs the tar (`sync_timedb_day_close_cooperation.py`).

**Validation read locks:** parallel raw-remove validation defaults to **`sync_archive_validation_max_workers=2`** (INI `[PIPELINE]`). Raise only when append/read-lock contention is acceptable.

**`sync_timedb_archive.py` (sealed-archive backfill CLI):** dispatches **one task per sealed daily archive** (`.tar.zst` / legacy `.tar.gz`) onto a `sealed-archive-pool` thread pool of **`sync_archive_pool_processes`** threads, with at most **`sync_timedb_archive_max_concurrent_sealed_days`** (default **1**, capped at the pool size) in flight through `imap_sliding_window_watch_pool` (context **`sync_timedb_archive pool`**). Before dispatch it prewarms the members store once per sealed day (`archive chunk prewarm begin sealed_paths=... days=...`, `Prewarming archive members store for day=... sealed=...`, `archive chunk prewarm complete elapsed_s=... days=...`). The watcher polls every **`sync_pool_poll_timeout_s`**; an empty poll may log `WARN: pool imap stall deferred: members-store populate active for day=...`, `... worker progress active ...` or `... long ingest budget ...` (rate-limited by **`sync_pool_stall_defer_log_interval_s`**). The tool has no poll-count abort (threshold **0**; `dynamic_stall_abort_after` / `dynamic_stall_wall_s` stay **0**), so a sealed day that never finishes keeps the process running: inspect DB locks, members-store populate, or a stuck member parse. A `MultiprocessingWorkerExitError` that reaches `main` logs `sync_timedb_archive exiting after pool worker death: ...` and exits through `_handle_pool_worker_exit_fatal` -> `hard_exit_pool_worker_error` (`Pool worker exit: hard exit code=<n> context=... likely_cause=...`, then `os._exit(<n>)`). Its thread pool has no worker processes, so the dead-worker (exit 137), idle-ghost and reconcile checks in `multiprocessing_pool_health.py` never trigger.

**Ingest sliding window:** The queue orchestrator keeps at most `sync_ingest_pool_processes` ingest leases in flight and **refills** on completion (hot vs catchup reserved slots).

**Dispatch order vs log order:** **`ingest file path=`** lines reflect completion order (parallel workers); they may permute among simultaneous dispatches. **Scheduling order** is in-process job-store ingest ZSET score bands (hot newest-first vs catchup oldest-first) under one orchestrator process.

**Parse-stage stall (DB-complete large raw):** When `head_timestamp_present_in_db` is true but the file is multi-MiB, a full `readlines()` plus full duplicate scan before any deadline checkpoint would keep a worker in top-level **`parse`** (no `duplicate_scan_streaming` substage) until abort. Guards: **head+tail DB probe** skips the duplicate scan when both seconds are present; **`sync_ingest_stream_duplicate_scan_bytes`** (default **8 MiB**) routes duplicate detection through the streaming path; **`sync_ingest_db_complete_tail_window_lines`** (default **500**) probes the tail timestamp window before a full-file duplicate scan on large head-present files; **`load_stats_file_lines` / `iter_stats_file_lines`** touch ingest progress and check the idle stall (`sync_ingest_stall_idle_s`) every 1000 lines / 1 MiB read; `_run_ingest_timed` wraps each worker task in idle-stall progress tracking with no wall timer.

**DB-complete ingest + sealed-only days:** When `archive_keep_uncompressed_tar=no`, DB-complete files (`outcome=db_skip`) call `raw_stats_path_needs_tar_append`, which must not stream the full `.tar.zst` once per file **across the ingest pool**. **`populate-pool`** workers (`sync_timedb:worker:populate-pool`) run sealed/tar streams; **ingest-pool** and **archive-pool** workers enqueue populate work and wait on the members store. **Populate wait suspends the idle-stall clock** (`respect_ingest_deadline=False`) - wait duration is bounded by populate stall/max limits. **When the members store is fully warm (`complete=1`, non-empty map), duplicate-check uses a single store point lookup per member - not a full-map dump per worker L1 miss.** When both sibling `.tar` and sealed `.tar.zst` exist and the store is warm, duplicate-check must not Nx parallel `get_existing_archive_members(tar)` under `file_read_lock_wait`. Per-process L1 plus **members store** coordinate **single-flight populate** per calendar day. The populate winner renews lock/progress on each store batch **and** on a derived heartbeat interval so slow sealed scans do not false-stall. Stall/timeouts raise `ArchiveMembersPopulateStalledError`. When populate cannot read a sealed archive, the winner classifies failure once (`zstd -t` vs tar stream), sets store **`archive_day_ingest_skip`**, and all workers skip tar-append duplicate-check for that day (**no** parallel per-worker point lookups). Ingest does **not** run local sealed scans (see **`sync-timedb-ingest-pool-io-coordination.mdc`**). **`populate_degraded` without day skip** raises `ArchiveMembersStoreUnavailableError` (no local zstd fallthrough). There is **no zstd decompress timeout** on the ingest lookup path. `sync_timedb` **hard-fails** mid-ingest duplicate-check on non-transient populate contract failure (`sys.exit(1)` - supervisord restart). Ingest member scans, seal and decompress all run plain zstd (no `nice`/`ionice`).

| `sync_timedb_archive_max_concurrent_sealed_days` | 1 | Sealed days in flight in `sync_timedb_archive.py` (capped at `sync_archive_pool_processes`) |

**Post-deploy `populate-pool` verification (`pipeline` logs):**

Run from the checkout containing `docker-compose.yaml`.

```bash
podman-compose -p hpcperfstats logs pipeline 2>&1 \
  | grep -E 'populate-pool|chunk prewarm' | tail -40
podman-compose -p hpcperfstats logs pipeline 2>&1 \
  | grep -E 'member stream failed|ingest per-file timeout' \
  | tail -40
```

Expect `sync_timedb:worker:populate-pool` with **`populate_source=tar`** when sibling `.tar` exists (active or closed days), or **`populate_source=sealed`** only when tar was dropped; **no** `ingest per-file timeout` from `ingest-pool` workers while the members-store populate lock is held and progressing (populate wait suspends the idle-stall clock; stall/max limits bound wait duration). `DB lock wait ... batch` must not appear. Outcome lines include `parse_elapsed_s=` / `postgres_s=` / `elapsed_s=`.

**Duplicate tar members:** `_run_day_close_job` runs a **`dedupe`** stage on the open `.tar` before seal (`dedupe_tar_keep_largest_file_per_member`, keeps the largest file per member name) only when the open daily `.tar` exists (`sync_timedb_queue_orchestrator.py:3083`; with no open tar the job takes the `no_tar_handoff` stage instead, `:3220`) and `skip_merge_remaining_raw` is false (`:3096`), then only after `reconcile_merge` and the second `pre_seal_verify` / `wait_on_ingest` checks return without yielding (`:3190-3198`). `skip_merge_remaining_raw` is set, so `reconcile_merge` and `dedupe` are skipped, when the coordinator phase is `done` and a sealed `.tar.zst` / `.tar.gz` sibling exists (`reason=phase_done_sealed`, `:3009-3012`), or when raw remains or a handoff is wanted but no append or hot ingest holds the tar (`reason=append_idle`, `:3040`). Log lines: `queue_orchestrator day_close stage_enter day=... stage=dedupe`, `queue_orchestrator day_close stage_exit day=... stage=dedupe result=ok|yielded|fail`, and on error `queue_orchestrator day_close dedupe fail day=... err=...`. Populate still records a members-store `dedupe_hint` for days with duplicate members; no production path reads it.

**Idle stall soft-requeue:** there is no internal wall-clock soft-kill. Soft-requeue uses **`sync_ingest_stall_idle_s`** (default **1800**) when parse/write heartbeats stop; Postgres **`statement_timeout`** remains the absolute DB ceiling.

For large DB sites with slow duplicate-detection or bulk writes, use **idle stall** (`sync_ingest_stall_idle_s`). Catch-up mitigations for sealed-only archives: **`archive_keep_uncompressed_tar=yes`**, tune **`sync_ingest_pool_processes`**, and rely on store **single-flight populate** warming the day map (not N parallel `zstd` per worker).
