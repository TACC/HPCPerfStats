# Monitor variables consumer map

Generated by `scripts/docs/gen_monitor_variables_consumer_map.py`; do not edit.

This page maps each monitor key to the consumer code that reads it, for developers who change monitor output or the analysis of `host_data`.
Per-key meaning, unit, width and tier are in [Monitor metrics reference](../../monitor/docs/METRICS_REFERENCE.md); this page adds the consumer side.
The monitor emits 39 types and 463 type and key pairs (347 distinct keys).

## Ingest data path

A monitor sample reaches `host_data` in these steps:

1. The monitor prints sample headers (`<TIME> <JOBID> <HOST>`), data rows (`<TYPE> <DEV> <VALUES>`) and `!<TYPE>` schema lines ([raw data format](../../monitor/docs/RAW_DATA_FORMAT.md)).
2. `hpcperfstats/listend.py` (`on_message`) appends each RabbitMQ payload to the per-host archive directory.
3. `hpcperfstats/dbload/sync_timedb.py` (`add_stats_file_to_db`) reads the archive files.
4. `hpcperfstats/dbload/lib/sync_timedb_parsing.py` (`parse_stats_lines`, `compute_deltas_and_arc`, `EVENTMAPS_BY_TYPE`) parses the lines, maps legacy `CTL*` and `CTR*` schema columns to logical event names, collapses multi-device rows and computes `delta` and `arc`.
5. `hpcperfstats/dbload/lib/io_helpers.py` (`host_data_instance_from_stats_row`) builds the ORM rows.
6. `hpcperfstats/site/lib/machine/models.py` (`host_data`) stores `time`, `host`, `type`, `dev`, `event`, `unit`, `value`, `delta` and `arc`.
7. Analysis (`jid_table`, `metrics`, `plot/*`) and the API read `host_data` by job window and schema.

The consumer stages read `host_data` in these modules (paths relative to `hpcperfstats/`):

| Stage | Modules |
| --- | --- |
| Job window and schema | `analysis/metrics/lib/gen/jid_table.py` |
| Job metrics | `analysis/metrics/lib/metrics.py` and `analysis/metrics/lib/columnar/`, stored in `metrics_data` |
| Summary plots | `analysis/metrics/lib/plot/summaryplot.py`, `analysis/metrics/lib/plot/summary_metric_descriptions.py` |

| API and Type Detail | `site/lib/machine/api.py` |
| UI tooltips | `site/frontend/src/utils/variableMetadata.ts` (`getDescriptionForVariable`), `variableMetadataMonitorEvents.ts` |

## Value sentinels

The wire codes are in [raw data format](../../monitor/docs/RAW_DATA_FORMAT.md#sentinels-values-the-monitor-could-not-read); the consumer catalog is `hpcperfstats/lib/monitor_sentinel.py`.
Ingest stores the code in `host_data.value` with `delta` and `arc` NULL, and every reader excludes `value < 0`.

| Code | Slug | Gap handling | Kind |
| --- | --- | --- | --- |
| -1 | `NOT_UPDATED` | bridgeable | transient |
| -2 | `NOT_PRESENT` | chain-breaking | static |
| -3 | `READ_FAILED` | bridgeable | transient |
| -4 | `PERMISSION_DENIED` | chain-breaking | static |
| -5 | `PMU_BUSY` | chain-breaking | transient |
| -6 | `NOT_SCHEDULED` | chain-breaking | transient |
| -7 | `BACKEND_ERROR` | bridgeable | transient |
| -8 | `INVALID_VALUE` | bridgeable | transient |
| -9 | `BACKOFF` | bridgeable | transient |
| -10 | `NOT_BUILT` | chain-breaking | static |
| -11 | `COUNTER_RESET` | chain-breaking | transient |
| other below 0 | `UNKNOWN` | chain-breaking | transient |

Bridgeable codes mean the source counter kept running, so the next valid sample's `delta` spans the gap; chain-breaking codes start a new chain.
Static codes mark a counter absent on that host; transient codes are gaps.
On `host_cpu_hw`, rows from a `$build` slug with `likwid` and no `x86perf` (or with no `$build` line) never bridge (`monitor_sentinel.bridge_proven`).
Researchers see only `NOT_PRESENT` as a no-data reason on Job Detail; staff views show every code.
