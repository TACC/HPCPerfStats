# Web UI metrics

This page defines every field, panel, metric and plot on the HPCPerfStats Job Detail page, and what each one helps you decide.
It is for researchers and HPC users reading their jobs; [Explore jobs in the web UI](../tutorials/explore-jobs-in-the-web-ui.md) walks the same page step by step.

> [!NOTE]
> Not every job or architecture has every signal.
> When data is missing, the panel or tab that would show it says so.

Numbers in brackets, such as [[1]](#ref-1), point to [Concept references](#concept-references).

## Scheduler fields

**Job overview** shows these fields from batch accounting (Slurm); they are the official record of the run.

| Field                     | What it is           | Diagnostic use                                                                                                |
| ------------------------- | -------------------- | ------------------------------------------------------------------------------------------------------------- |
| **Job ID**                | Unique scheduler ID  | Cross-reference logs, support tickets and reproducer scripts.                                                 |
| **User**                  | Submitter            | Ownership and fair-share context.                                                                             |
| **Project**               | Charge or allocation | Which allocation was charged.                                                                                 |
| **Start** / **End**       | Scheduler window     | Align with external logs; spot an unexpected early end.                                                       |
| **Run time (s)**          | End minus start      | Compare with the requested limit: far below it means over-requesting; at it means the job may have timed out. |
| **Queue**                 | Partition or class   | Explains hardware policy (GPU or CPU, debug or production).                                                   |
| **Job name**              | User-provided label  | Often encodes the experiment or binary name, a quick sanity check.                                            |
| **Status**                | Completion outcome   | Failed jobs can still have partial telemetry worth opening.                                                   |
| **Cores / nodes** (cores) | Allocated core count | Match it to how you launched MPI [[9]](#ref-9) or OpenMP [[10]](#ref-10); a miscount means wrong binding.     |
| **Cores / nodes** (nodes) | Allocated node count | Multi-node imbalance metrics and network plots only make sense in this context.                               |

## Panels and tabs

The Job Detail page has these surfaces:

| Surface                 | Content                                                                                                                                                                                                                                         | Diagnostic use                                                                                                         |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Print**               | Browser print or Save as PDF of Job overview, Resources, Metrics, Summary plots, Roofline and Multiprecision Mix                                                                                                                                | A triage packet for support tickets or offline review without copying each tab by hand.                                |
| **Job overview**        | Job ID, status, runtime, queue, user and project, cores and nodes, start and end                                                                                                                                                                | Fast triage before telemetry.                                                                                          |
| **Resources**           | Cards in order: watt-hours (when present), **GPU Information** (aggregate stats, with the per-host, per-device inventory behind a collapsed control), **Shared File Systems**, then **Client / Server** log links; GPU order NVIDIA, AMD, Intel | Check energy, GPU allocation against activity, and I/O [[11]](#ref-11) volume, then jump to external logs.             |
| **Metrics**             | Job-level metrics, one card per section (see [Job-level metrics](#job-level-metrics))                                                                                                                                                           | Scan CPU, fabric and GPU scalars without scrolling past unavailable rows.                                              |
| **Summary plots**       | Host-level timelines of CPU, memory, NUMA [[4]](#ref-4) and DRAM, fabric and file system, GPU and node power                                                                                                                                    | First visual scan for phase changes, host outliers and cross-signal coupling (GPU drops while fabric spikes).          |
| **Roofline**            | CPU roofline and GPU roofline (memory bandwidth when available, else PCIe or NVLink [[7]](#ref-7))                                                                                                                                              | Tell compute-limited from bandwidth- or link-limited work and pick the right optimization.                             |
| **Multiprecision Mix**  | CPU and GPU precision-activity pies                                                                                                                                                                                                             | Check that the run uses the expected mixed-precision paths [[6]](#ref-6) and catch drift across runs or code versions. |
| **Processes**           | Process names, each with expandable host groups; the group header shows average Peak VM, HWM, Stack, Text, Libs and Threads; the memory columns are in MB and are the job-level high water for that process name                                | Confirm what ran and its memory footprint (wrappers, launch depth, wrong environment).                                 |
| **Execution and hosts** | XALT executable path, working directory, library set and host list                                                                                                                                                                              | Spot environment drift, module or library mismatches, and host-level problems.                                         |
| **Device data**         | Monitor type names and recorded events, linking to type detail pages                                                                                                                                                                            | See which counter families were collected and drill into one type.                                                     |

### Device data table

The **Type Name** column lists each monitor type present for the job, such as `host_cpu`, `host_mem`, `nvidia_gpu`, `host_ib`, `lustre_llite` and the hardware counter families.
The **Recorded Performance Events** column lists the event names recorded.
Jobs from older monitors list legacy type names such as `cpu` or `mem` with or instead of the canonical names.
GPU memory counters appear as `gpu_mem_util` and `gpu_mem_used_mb`; older monitors record `mem_util`.
Select a type name to open its type detail page.

### Type detail page

- **Rates Aggregated over devices**: a plot of rates aggregated over the type's devices.
- **Counts Aggregated over devices and hosts**: a table of means across hosts and devices for each event at each time offset from the first sample, for reading numbers without hovering the plot.

### Host plot

The host plot shows one host over a time window you choose, by default about the last day.
Use it to debug a node outside a single job: a noisy neighbor, a hardware fault, or a post-mortem on a monitored login or service node.

## Shared nodes

When a job shared a node with other jobs, CPU and GPU metrics and plots cover only that job's cores and GPU devices when those are known.
Memory summaries use the job's cgroup memory.
On such a job, the **?** help of a counter that stays node-wide ends with a red note saying it is not limited to this job.
Job-scoped CPU, GPU and cgroup memory signals carry no note, and exclusive jobs never show it.

## Job-level metrics

The **Metrics** tab groups rows in this order: CPU, GPU, File System, Network, Misc.
Memory and NUMA rows sit under CPU; InfiniBand, Omni-Path, Ethernet and LNET rows sit under Network.
Network always appears, with **Data not available.** when it has no rows; the other sections appear only when they have a row.
In each section, rows with a value come first and rows without one sit in a collapsed **Metrics not computed** table.

### Metrics without a value

A row without a value says **Data not available.** unless the page has something you can act on.
Two messages are shown to every user:

- `<COLLECTOR> collector not found on this node's monitor` (for example `host_ib collector not found on this node's monitor`): the monitor on the job's nodes does not collect that family, such as a node without an InfiniBand adapter.
  The metric does not exist there; nothing went wrong with the job.
- `<COLLECTOR>: counter not present (n/N hosts)`: the collector runs, but the hardware counter does not exist on n of the N nodes.
  Compare with jobs on other node types before reading anything into the gap.

`<COLLECTOR>` is a monitor type name.
Other causes (a failed read, counters busy with another tool, a monitor update in progress) are temporary site-side conditions shown as **Data not available.**; the site team sees the details.
When such a gap is short, the value is computed from the readable samples and shows without a note.

## Plot surfaces

These are the Job Detail surfaces beyond scalar metrics.
Pair each with the **Metrics** tab: plot peaks often explain extreme scalar maxima [[12]](#ref-12).

### Summary plots

- Summary is the fastest phase and host-outlier scan across CPU, memory, network, I/O and GPU traces.
- When InfiniBand, Ethernet or Omni-Path error counters have non-zero rates, the grid adds one subplot per counter, each line one host over time, with the same **?** help as other subplots.
- Time axes and hover use the cluster time zone from site configuration, not UTC.
- When IMMA, HMMA and DFMA tensor splits exist, Summary shows one tensor-pipe subplot per kind; the lumped tensor series appears only without splits.
- A point whose counters could not be read is left out rather than drawn too low.
  A short gap inside a host's line is bridged by a straight line between its neighbors [[17]](#ref-17), the same way the job metrics treat it.
  A gap at the start or end of the job, or a long one, stays empty.
  The same rule applies to roofline points and type detail plots; peak values use only samples that were read.

### Roofline tab

The Roofline tab separates compute-ceiling from bandwidth- or link-ceiling regimes in the roofline model [[1]](#ref-1).
Check your reading against `avg_flops` [[3]](#ref-3), `avg_mbw`, `avg_gpu_mem_bw_gbps`, `max_gpu_link_gbps` and the fabric ratios.

- CPU roofline: points near the sloped bandwidth line are memory-bandwidth limited; points near the flat top are compute limited.
- GPU roofline: each coral point is one host, GPU device and time sample, not a sum over the node's GPUs.
  The title names the bandwidth axis: **GPU Roofline (Memory BW)** when estimated GPU memory bandwidth samples exist (the Summary HBM signal), else **GPU Roofline (PCIe/NvLink)** from interconnect byte rates.
  Low arithmetic intensity [[2]](#ref-2) phases are HBM- or link-limited by that title; high-intensity phases can be tensor- or core-compute limited.
  GPU scaling limits can come from PCIe or NVLink [[7]](#ref-7) rather than kernel math, especially under the PCIe/NvLink title.
  The device inventory is on Resources; this plot is the per-device arithmetic intensity view.
- Memory- or link-limited phases gain from locality, data layout, batching or communication changes; compute-limited phases gain from kernel efficiency, vector or tensor use and occupancy [[8]](#ref-8).
- Hovering the roof line shows **Peak performance (GFLOP/s)** and **Peak bandwidth (GB/s)** as plain decimals, with axis units FLOP/byte and GFLOP/s.
  Hovering a job point shows host, device (`-` when blank), arithmetic intensity, performance and time.
- When one chart is still loading or unavailable, the ready one appears first; Multiprecision Mix stacks the same way.

### Multiprecision Mix tab

The pies show mixed-precision path composition [[6]](#ref-6) as shares of busy arithmetic rates only, with no idle wedge.
Each pie includes only the precision widths with usable positive metrics for the job and architecture.
When counters were collected but every rate is 0, the pie says the telemetry is present but idle, which differs from counters never collected.
When a change alters the precision policy, compare this tab first, then the throughput and utilization numbers.

CPU pie:

- Wedges are FP64, FP32 and FP16 (`avg_fp64_instr`, `avg_fp32_instr`, `avg_fp16_instr`) plus INT16 and INT8 (`avg_arm_int16_ops`, `avg_arm_int8_ops`).
- On Grace and Intel the pie counts instructions, not FLOPs: one vector instruction counts once, so it shows which precisions the code uses, not how much arithmetic each did.
- On AMD Zen5 the CPU counts only FLOPs by precision, so the FP64 and FP32 wedges are FLOP shares.
- AMD Zen3 and Zen4 (such as Lonestar6 Milan nodes) have no precision split and show no CPU pie ("not available"); use `avg_flops` for their FLOP rate.

GPU pie:

- Each wedge is a pipe's busy share (how much of the time it worked), not its FLOP share; a pipe busy half the time can still do far fewer operations than another.
  Hover shows the share of busy percent.
- Wedges, when positive: **Tensor IMMA (INT8/INT4)**, **Tensor HMMA (FP16/BF16/TF32/FP8)**, **Tensor DMMA (FP64)** (Hopper and Blackwell only), **Tensor (unattributed)**, **FP16**, **FP32**, **FP64** and **Integer pipe**.
- **Tensor (unattributed)** is total tensor activity minus HMMA, IMMA and DMMA, shown only when splits exist and the remainder is more than a tiny amount.
  Without splits the whole tensor activity is one **Tensor** wedge.
- HMMA is one counter for FP16, BF16, TF32 and FP8, so the pie cannot split those precisions and any tensor FLOP figure from it is an estimate.
- No DFMA wedge exists: DFMA is the FP64 pipe (equal to FP64 on Hopper and Blackwell), so it would count FP64 twice.
  FP64 work appears as **FP64** (pipe) and **Tensor DMMA (FP64)** (tensor cores).
- **Integer pipe** is busy under FP work on Hopper (about half the time) and near 0 on Blackwell; compare it only between jobs on the same GPU generation.
- On Blackwell, GB200 (Horizon) and RTX PRO 6000 (Stampede3 amd-rtx) nodes count tensor work in the GPU FLOP rates behind the GPU Roofline points, using tensor peaks measured on the clusters.
  GB200 counts FP16, BF16 and FP64 tensor work; RTX PRO 6000 counts FP16 and BF16 only, since its FP64 matrix math does not use tensor cores.

### Resources panel

Resources gives a quick check of I/O volume, burst peaks and GPU occupancy before plotting.
Lustre, NFS and BeeGFS rows each appear when that client has data for the job.
If the totals, **Peak MB/s** or **Peak IOPS** are high, check `avg_sharedfs_bw`, `avg_sharedfs_iops`, `max_mds` and `max_lnetbw` for the bottleneck type [[11]](#ref-11).
GPU statistics sit above the log buttons, so you read file system and accelerator context before opening logs.

### Execution and hosts tab

The tab detects environment drift (wrong module, library or container path) and host-specific anomalies.
For a regression with the "same script", check this tab before tuning code.

### Device data tab

The tab confirms which counter families and events were collected for the job.
Check it for the expected families before interpreting plots or metrics.

## Symptom checklist

Each row lists the metric keys from [Metric catalog](#metric-catalog) to read and what to check next.

| Symptom                               | Signals                                                                                                                                                                         | Check                                                                                                               |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| Job did not run the intended workload | Short runtime, flat or empty Summary traces, empty process list                                                                                                                 | **Execution and hosts** (path, working directory, library set), **Processes**, the scheduler record                 |
| Timeout or preemption risk            | Runtime near the requested limit, abrupt trace cutoff                                                                                                                           | Tail-end spikes in file system, fabric or GPU activity; adjust the time limit or checkpoint cadence [[13]](#ref-13) |
| Host memory pressure or OOM risk      | High `mem_hwm`, elevated `max_numa_remote_rate`, high `dram_bw_node_imbalance`                                                                                                  | First-touch policy, rank and thread placement, per-rank memory growth                                               |
| GPU memory or accelerator under-use   | Low `avg_gpuutil`, low `avg_tensor_active`, low `detail_gpu_util_mean` with full `detail_gpu_count`                                                                             | Input staging, device mapping, kernel size, launch configuration                                                    |
| Communication-dominated scaling       | High `avg_ibbw`, `max_fabricbw`, `avg_fabric_mb_per_gflops`, `avg_fabric_mb_per_avg_tensor`, `max_packetrate` peaks [[15]](#ref-15)                                             | Decomposition, collective strategy, message size (`avg_packetsize`), rank mapping                                   |
| File system or metadata bottleneck    | High `avg_sharedfs_iops`, `max_mds`, `max_lnetbw`, large **Shared File Systems** totals                                                                                         | File-per-rank patterns, small sync writes, metadata-heavy loops                                                     |
| Throttling or power limits            | Named flags in `max_gpu_clock_event_reasons`, high `max_gpu_power`, capped `max_node_power_est_w` with performance dips                                                         | Power caps, thermal conditions, cluster policy limits                                                               |
| Cross-node imbalance or stragglers    | Elevated `node_imbalance`, `flops_node_imbalance`, `gpu_util_node_imbalance`, `tensor_node_imbalance`, `fabric_node_imbalance`, `lnet_node_imbalance`, `dram_bw_node_imbalance` | Domain decomposition, skewed rank placement, node health                                                            |
| Gaps in plots or metrics              | Missing points, straight segments, missing plots for one family                                                                                                                 | See the next list                                                                                                   |

For gaps in plots or metrics:

- Check **Device data** for the expected signal families and compare with similar jobs.
- A **Metrics** row reading "collector not found" or "counter not present (n/N hosts)" means the signal does not exist on those nodes; it is not a gap in your job.
- A straight segment over a few samples in a Summary or type detail line is a short read gap filled between its neighbors, not a measured plateau.
- A plot missing for one family means the gaps were too long, or at the edge of the job, to fill.
